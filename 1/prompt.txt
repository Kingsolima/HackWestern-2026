What I found that the plan depends on:

Events arrive on plain onmessage (no named SSE events). The server replays after Last-Event-ID, and the browser sends that header automatically on reconnect.
The reconnect trap: when a job ends the server closes the stream, and EventSource auto-reconnects. The server then returns nothing and closes again, so the browser loops every ~3 s. The UI must close the EventSource itself on a terminal stage (DONE | DEGRADED | FAILED).
run_started.live / run_finished.live say whether a run is live. A replayed run's streaming_url is dead.
Settings: recordings_dir (env RECORDINGS_DIR), default data/recordings. Compose mounts ./data:/data:ro, so live recording fails on the server.
BRACKET_T (cad robot.py) duplicates BRACKET_THICKNESS_MM (backend checks.py).
